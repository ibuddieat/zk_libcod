json_save_async( <fs path>, <value>, [<pretty>] )

Module: System

Summary:

Non-blocking variant of json_save. The cJSON tree is built from the GSC value on the main thread (this is fast for typical data; KB-scale finishes in microseconds). A detached worker thread then handles the slow parts (printing to text + writing to disk) and the call returns control to GSC immediately with a jobId.

Poll json_async_done() for the jobId, then call json_async_result(jobId) to get a 1/0 success flag.



Example:

job = json_save_async("stats/match_log.json", level.matchLog, 1);
// continue gameplay, don't block
// ...
done = json_async_done();
for(i = 0; i < done.size; i += 1)
    if(done[i] == job)
        ok = json_async_result(job); // 1 = written, 0 = error



Required Args:

  • 1 : <fs path> Path relative to the mod root. No absolute paths, no .., rejected at submit time.
  • 2 : <value> Any GSC value (struct, array, string, int, float, vec3).

Optional Args:

  • 3 : <pretty> 0 compact single-line (default), 1 indented multi-line.

Returns:

Integer jobId >= 1 on successful submission, 0 on failure (invalid path, queue cap reached, value build error, thread create error).


Notes:

  • Workers use plain libc fopen/fwrite (not the engine FS; FS_* is not thread-safe). Files land under fs_homepath/<mod>/.
  • The GSC value tree is materialized on the MAIN thread before submission, so any modifications made to the value after the call are not seen by the worker (snapshot semantics).
  • Pending job cap: scr_json_async_max_jobs (default 64).
  • Always call json_async_result(jobId) for every successfully submitted job, or the job struct leaks.
