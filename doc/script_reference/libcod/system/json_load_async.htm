json_load_async( <fs path> )

Module: System

Summary:

Non-blocking variant of json_load. Spawns a detached worker thread that opens, reads and parses the file off the main script VM, then returns control to GSC immediately. Returns an integer jobId >= 1 on success, or 0 if submission failed (bad path, queue full).

Poll json_async_done() for the jobId, then call json_async_result(jobId) to claim the parsed value.



Example:

job = json_load_async("stats/big_archive.json");
if(job == 0)
    return; // submission failed (logged via stackError)

// later, after periodic polling:
done = json_async_done();
for(i = 0; i < done.size; i += 1)
    if(done[i] == job)
        wp = json_async_result(job);



Required Args:

  • 1 : <fs path> Path relative to the mod root. Must NOT be absolute (start with /) and must NOT contain .. segments, rejected at submit time for sandbox safety.

Returns:

Integer jobId >= 1 on successful submission, 0 on failure (invalid path, queue cap reached, thread create error). On 0, a stackError is logged with the reason.


Notes:

  • Workers use plain libc fopen (not the engine FS), so files inside loaded .iwd archives are NOT searched; only on-disk files under fs_homepath/<mod>/. For iwd content keep using sync json_load.
  • Worker hard-cap: rejects files larger than 32 MB outright (i386 address-space safety). The worker also honors scr_json_max_load_bytes snapshotted at submit time.
  • Pending job cap is scr_json_async_max_jobs (default 64). Submissions over the cap fail with jobId 0.
  • Always call json_async_result(jobId) eventually for every successfully submitted job; otherwise the job and its parsed yyjson tree leak.
